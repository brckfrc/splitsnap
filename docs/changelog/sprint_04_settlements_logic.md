# Sprint #4: The Settlement Screen Adds Up (July 2026)

Client-only, no migration. All of it came out of one user report — "after settling some of the suggested payments and adding more expenses, the numbers blow up and it doesn't count the payments" — and the production audit that ruled out bad data as the cause.

- **Bad data was ruled out first.** `supabase/audit/expense_integrity_audit.sql` against production: queries 1, 3 and 4 returned no rows (nothing whose shares or payers fail to add up, no allocation to a non-member, no expense without a payer) and query 2 puts `net_toplam` at exactly `0.00` for every group. So the ledger was right and the screen was wrong, which is what made this a UI sprint instead of a repair job.
- **The breakdown now accounts for settlements, so it reconciles with the headline.** `Harcama Dökümüm` was built only from expenses while **Sizin Net Bakiyeniz** above it included settlements. The moment a payment was recorded the two numbers diverged and nothing named the difference; every later expense moved both while the gap stayed, so it read as drift rather than as one missing line. The section is now **Bakiye Dökümünüz** with a KAYITLI ÖDEMELER block and a three-line footer (Harcamalar / Ödemeler / **Net bakiyeniz**). Each payment row carries its signed effect on *your* balance, not just its amount, so the rows visibly sum to the figure at the top.
  - Each row's effect is computed with the same expression as `calculateBalances` rather than a simpler outgoing/incoming flag. That is not defensive styling: `settlements` has no `from_user_id <> to_user_id` constraint, and a row pointing at yourself nets to zero in the balance while a flag would show it as a credit — the breakdown would stop adding up again, for a new reason.
  - Near-zero amounts are normalised before display, so accumulated float drift can no longer render a red `-₺0,00`.
- **A recorded payment now reaches the other devices.** `settlements` was in the realtime publication since Week 4 but no client ever subscribed to it, so after someone recorded a payment everyone else kept being offered the suggestion that was already acted on until they backgrounded and resumed the app. Now subscribed on the existing group channel, filtered on `group_id`.
  - **Scope review, deliberately narrow:** `expense_shares` / `expense_payers` were considered and rejected as redundant — both RPCs always touch the parent `expenses` row, so a split change already arrives as an `expenses` event and the handler refetches shares and payers with it. `profiles` is cosmetic (a renamed member) and worth it only when avatars land; `friend_requests` has no feature yet. The reload strategy is the reason to stop here rather than add more, and it is now its own backlog item.
- **Acting on a stale suggestion is no longer silent.** The Öde button recorded whatever amount was on screen when it was rendered. Confirming now refetches, re-derives the suggestion from fresh balances, and branches: if the pair is no longer suggested it says the debt is closed and warns that saving anyway creates a reverse debt; if the amount changed it offers the current figure *and* the original one. Overpaying is still allowed — people do settle up generously — it just has to be a choice rather than an accident. This is the client half of the missing subscription above, and one of the two possible explanations for the reported confusion.
- **Duplicate confirmation dialogs and the missing spinner:** the in-flight flag was only set *after* the user confirmed, so rapid taps stacked Alerts. It is now a ref flipped synchronously in the tap handler, and the pending row is tracked by key so only the button being used shows a spinner while the others disable.
- **One money parser for values coming out of the database:** `settlements-supabase.ts` was the single place a `numeric` column skipped the string-to-number step, on a row typed `any`. A settlement amount arriving as `"50.00"` would turn a balance accumulator into a string and make every later comparison read as garbage. The helper is now `parseNumeric` in `utils/numeric.ts`, shared with `expenses-supabase.ts` and named to distinguish it from `parseAmount` in `utils/validation.ts`, which parses what a *user* typed. Typing the row immediately surfaced a second latent bug the `any` had been hiding: `note` is nullable in the database but `string | undefined` in the domain type.

**The group it was reported in, for the record.** In *istanbul*, Arda paid 11.196,50 with a 6.052,26 share, so expenses alone leave him **+5.144,24**; settlements sent his way total **5.494,17**, and the 349,93 difference is exactly the debt shown against him. Two histories produce that same end state and the totals cannot tell them apart: either he was paid back in full and *then* new expenses pushed him into debt, or someone acted on a suggestion that had already gone stale. This sprint addresses both — the first is now explained by the breakdown, the second is now caught at confirm time — but if you want to know which actually happened, order the group's expenses and settlements by `created_at` and find the event where his running balance first goes negative. A payment there means stale suggestion; an expense means the natural story.
