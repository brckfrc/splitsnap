# Sprint #2: Split Payer & Premium UI Upgrade (July 2026)

- **Editing an Expense Was Completely Broken (`invalid input syntax for type uuid: ""`):** Saving *any* edit failed with a raw Postgres error. The permission check in `update_expense_with_shares` read `coalesce(_owner_id, '') <> _uid`; since `_owner_id` is a `uuid`, COALESCE resolved to `uuid` and the empty-string literal was coerced to `uuid` at **plan** time, so the statement raised before any value was ever compared. That made the failure unconditional rather than an edge case, and it shipped in the multi-payer migration (`20260726172500`) where the RPC was rewritten. Adding an expense was unaffected because `create_expense_with_shares` has no equivalent check. Fixed in `20260727051500_fix_expense_update_owner_check.sql` with `_owner_id is distinct from _uid`, which handles a null owner correctly without a cast (the old COALESCE was presumably guarding exactly that case). Server-side only, no client change or rebuild needed. **Caught while seeding screenshot data, i.e. one commit before submitting 1.2.0.**
- **AI Spend Is Now Bounded (`parse-receipt`):** The receipt-parsing edge function had authentication but no budget: being a signed-in user was the only requirement for making an OpenAI call, with no size ceiling and no call ceiling, so cost was effectively unbounded.
  - **Two ceilings, both tunable without a deploy.** `20260727012000_ai_usage_quota.sql` adds `app_config` (a key/value table) holding `ai_daily_limit` (50 per user) and `ai_global_daily_limit` (500 project-wide). Either can be changed with a single `UPDATE` from the Supabase SQL editor, no migration and no function redeploy. The project-wide ceiling matters because a per-user limit alone is meaningless while signup is open and email confirmation is off: someone scripting account creation would simply get 50 calls per account. At current gpt-4o-mini pricing the global ceiling caps worst-case spend around 0.20 USD/day.
  - **Counter design.** `ai_usage` holds one row per user per day. Both it and `app_config` have RLS enabled with **no policies at all**, so they're unreachable from PostgREST entirely; only the `SECURITY DEFINER` `consume_ai_quota()` touches them, and it resolves the caller from `auth.uid()` itself rather than trusting an argument. The increment is a single atomic upsert so concurrent calls can't both read an under-limit count and proceed. Limit lookups `coalesce` to safe defaults, so a missing config row fails closed rather than into unlimited spend. Rejected calls still increment, so probing for the ceiling isn't free.
  - **Edge function.** Rejects oversized bodies on `Content-Length` before `req.json()` ever buffers them; clamps text to 6k characters keeping the head and the tail (merchant name is at the top of a receipt and the total at the bottom, so a plain truncation would discard the most important field); consumes quota before spending anything and returns 429 when it's gone; and wraps the OpenAI call in a try/catch returning 502, where a provider error was previously an unhandled rejection.
  - **No client contract change.** `parseReceiptText` already falls back to the local heuristic parser on any failure, so a user past quota quietly gets the weaker parser instead of an error. The same 6k clamp is applied client-side so a long receipt is shaped on the device rather than relying on server truncation.
- **Expense Detail Sheet in Settlement Ledger:** Each "Harcama Dökümüm" row was trying to fit the title, total, date, "Ödedi ₺X" and "Payı ₺Y" into one card row, so the 11pt meta line was truncated on nearly every entry and the numbers that explain the net were the first thing to get cut. Rows are now tappable and open `ExpenseLedgerSheet` (`components/settlement/expense-ledger-sheet.tsx`): full date, total, the complete payer and participant lists with each person's amount (current user marked "Sen"), and an ödediğin / payına düşen / bakiyene etkisi breakdown that shows how the net was derived, plus a shortcut into the expense itself. With the detail one tap away, the row meta line is down to date and total, which always fits. Added `formatLongDate` to `utils/format.ts`. The sheet's section rules are derived from `mutedForeground` at 25% rather than the `border` token: `border` is tuned for card edges against the page background and is nearly invisible *inside* a dark-mode card (`#1c1c1e` on `#121214`).
- **Full-Screen Receipt Viewer:** Tapping either receipt preview (add-expense or expense edit) now opens a new reusable `ImageViewerModal` (`components/ui/image-viewer-modal.tsx`): full-screen, pinch-to-zoom up to 5×, pan while zoomed, double-tap to toggle 1× / 2.5×, and a close button. Built on the already-installed `react-native-gesture-handler` + `reanimated`; no new dependency. The inline previews deliberately stay on `resizeMode="cover"` (a tight cropped strip looks better in the form than a letterboxed full receipt); a zoom badge in the corner signals that the full image is one tap away. A receipt that fails to fetch or decode now hides the whole **Fiş** section instead of showing an error row: receipts uploaded before the ArrayBuffer upload fix point at zero-byte objects that will never load, and since the edit screen has no re-upload UI there is nothing the user could do about it. Those expenses simply read as receipt-less, so no backfill migration is needed.
- **Any Member Can Invite:** Sharing a group invite was gated behind `isOwner`, which looked like a permission rule but never was one: RLS lets every group participant SELECT the group row including `invite_code`, the client already loads it into every member's local store, and `join_group_by_invite` accepts a valid code from any authenticated user. The gate was cosmetic (originally about not showing an empty invite row to members) while adding real friction, since only the founder could add someone. The invite code line and share button are now visible to every **active** member (`left_at IS NULL`); members who have left the group don't get them. A genuine restriction, if ever wanted, has to be enforced server-side rather than by hiding a button.
- **Expense Ordering by Entry Date:** Expenses carry two different dates: `date` (when the money was spent, chosen by the user) and `created_at` (when the row was entered). Everything sorted by the former, so a receipt typed in today but dated three weeks ago buried itself mid-list and looked like it hadn't saved. The home **Son Hareketler** feed now sorts by entry date, which is what "recent activity" means, and shows a relative label (Bugün / Dün / 3 gün önce, falling back to an absolute date past a week) so the ordering is self-evident. The group expense list keeps the spend date as its default (it reads as a ledger) and gains a small toggle in the section header to switch to entry order; in that mode each row's meta line shows "Eklendi <tarih>". Shared helpers live in `utils/expense.ts`, plus `formatRelativeDay` in `utils/format.ts`. `created_at` was already being selected in `EXPENSE_COLUMNS` but discarded by `mapExpenseRow`, so this only needed mapping it onto a new optional `Expense.createdAt`: no migration, no data change. The field is optional and falls back to `date` because expenses cached in MMKV before this change don't carry it until the next sync.
- **Invite Share Copy + Duplicated Link Fix:** Sharing an invite to WhatsApp pasted the URL twice. `shareInviteCode()` passed **both** `url` and `message` to `Share.share()`; iOS hands those to `UIActivityViewController` as two separate activity items and single-text-field targets concatenate them, appending the URL that was already inside the message body. Fixed by dropping `url` and keeping the link in `message` only; previews aren't lost, since WhatsApp and iMessage linkify plain-text URLs themselves. The copy now leads with the inviter's name (`Bora seni "Gıbrıs Gezisi" grubuna davet etti 💸`) so it reads as a personal invitation rather than a product ad, and presents the link and the code as equal paths instead of framing the code as an "if the link fails" fallback.
- **UI Copy Pass:** Rewrote the Gruba Katıl hint, which described our implementation rather than the user's action ("kodu otomatik ayıklarız"), as "Davet kodunu girin. Size gönderilen mesajın veya bağlantının tamamını yapıştırmanız da yeterli." Also removed em dashes from user-facing strings in favour of commas and colons (they stay in code comments and as the "no value" placeholder glyph), and brought the new receipt-scan warnings back to the formal *siz* voice used by the rest of the expense form.
- **Receipt Upload Was Never Sending the Image (root cause of the "receipt photo doesn't show" bug):** `uploadReceipt()` passed a `Blob` (from `fetch(uri).blob()`) to `supabase.storage.upload()`. supabase-js wraps a `Blob` in a `FormData`, and React Native's `FormData.getParts()` can only serialise `{ uri, name, type }` parts — a Blob is spread into a plain `{ _data: … }` object, so the request went out **without the image bytes**. The upload returned success, a `receipt_storage_path` was saved, and the expense detail screen then rendered a blank box from an unusable object. Switched to the ArrayBuffer path Supabase documents for React Native: `manipulateAsync(…, { base64: true })` → `base64-arraybuffer.decode()` → upload, with explicit guards for an empty encode result. The viewer code in the expense edit screen was correct all along and never needed changing, it just never had a real image to show. **Receipts uploaded before this fix stay broken**; rather than migrating them, the edit screen now hides the receipt section whenever the image can't load, so those expenses simply read as receipt-less. Verified at the code level (supabase-js body branching + RN `FormData` serialisation both read from `node_modules`); still needs an on-device end-to-end test.
- **Silent Receipt Failures Made Visible:** The `catch {}` around `uploadReceipt` in the add-expense screen swallowed every upload error, which is why the bug above looked like a broken viewer rather than a broken upload. It now shows a "Fiş yüklenemedi, harcama kaydedildi ama fiş fotoğrafı yüklenemedi" toast while still saving the expense. The expense edit screen likewise no longer renders a blank 180px box when the image can't be fetched or decoded; a failed signed URL or a failed `Image` load hides the receipt section entirely.
- **Receipt Reset/Replace Fixed:** Replacing a receipt only updated the date, because title and amount were guarded by `!title.trim()` / `!amount` — once the first scan filled them, the second scan was locked out — while the date had no guard at all and clobbered the user's manual pick. Autofill now tracks *ownership*: a field is rewritten only while it is empty or still holds the exact value the previous scan wrote, so a replacement receipt refreshes its own values but never overwrites what the user typed. The date, which has no empty state, is tracked by whether the user has opened the date picker instead. Removing the photo now also clears the values that receipt filled in (leaving user edits and the date alone).
- **Receipt Scan Validation Warning:** The receipt OCR flow no longer claims success when it found nothing. `parseReceipt()` now returns a `ReceiptScan` (`{ status, result }`) instead of a bare result, distinguishing **filled** (at least one usable field), **empty** (text was read but nothing receipt-like could be parsed), **no_text** (OCR found no readable text — likely not a receipt photo) and **failed** (OCR itself threw: unsupported device, unreadable file). It never throws, so the previously silent `catch` in the add-expense screen is gone. The status line under the receipt thumbnail renders a matching ⚠️ warning for each failure mode, plus a distinct "tutar bulunamadı, elle girin" warning when a receipt parsed but the total is missing. Fixes the bug where an all-empty parse still displayed **"✓ Otomatik dolduruldu"** with no amount, date or merchant; such a result is also no longer persisted to the expense's `ocr_suggestions`. Note that `currency` alone doesn't count as a usable field — a stray "$" or "TL" in arbitrary text isn't evidence of a receipt.
- **Dashboard Quick Wins:** Fixed the home **Son Hareketler** deep-link — tapping a recent expense now opens that expense (`/groups/[groupId]/expenses/[expenseId]/edit`, the app's canonical expense view) instead of just the group. Relabelled the **Bu Ay** figure as **"Bu ayki harcaman"** so it's clear the amount is the user's own share of this month's expenses rather than the group total. Removed the unused `@/global.css` import from `constants/theme.ts` and deleted the now-orphaned web-only CSS file (iOS boilerplate cleanup).
- **⚠️ Bitwarden / iOS AutoFill Freeze — investigated, no app-side fix (OS-level):** Repro: on the login screen, tap the e-mail field → AutoFill → Passwords → "fill username only" for the `splitsnap.borak.dev` Bitwarden entry → returning to SplitSnap freezes the UI to touch (keyboard won't open either). Diagnosed with runtime instrumentation (1s heartbeat + AppState + root `onTouchStart` probe): after returning, the **JS thread stays fully alive** (heartbeat ticks 20s+) but **no touch reaches the RN root** and RN **can't even present its own `Modal`** — proving a **native iOS window sits above the app at a high window level and swallows all touches** (stuck AutoFill / `UITextEffectsWindow`), i.e. NOT a JS/React problem. Attempts that did **not** work: `Keyboard.dismiss()`, present/dismiss `Modal` to re-key, native `AppDelegate` `didBecomeActive → window.makeKeyAndVisible()`, and native enumeration hiding all non-app windows. RN maintainers confirm these AutoFill quirks are Apple bugs unfixable without private APIs. Most likely user-side trigger: a too-high Bitwarden vault KDF (e.g. Argon2id 512MB) exceeding the AutoFill extension's ~120MB budget and hanging on return (bitwarden/mobile#3225). Workaround: lower KDF to default (PBKDF2 / Argon2id 64MB), or toggle iOS Settings → Passwords → AutoFill off/on + restart. **No code change shipped; all debug instrumentation and the experimental native workaround were reverted.** Revisit if Apple/Bitwarden ship a fix.
- **Password Visibility Toggle & AutoFill Append Fix:** Added an optional `secureToggle` (eye/eye-off) affordance to the shared `Input`, wired into every password field (login, register, change-password ×3, delete-account). Beyond the show/hide convenience, revealing the password also works around iOS's native "clear secure field on first edit after AutoFill" behavior — so users who append extra characters to a password-manager-filled value (e.g. Bitwarden) can now do so without the field wiping itself.
- **Forced Re-Login After Password Change:** After a successful password change, the app now signs the user out and routes them back to the login screen (toast: "Lütfen yeni şifrenizle tekrar giriş yapın"). This is both a security best-practice (re-authenticate after a credential change) and the reliable path for password managers to offer an **update** prompt — the login submission flow is where iOS/managers detect credential changes, whereas in-app change-password screens don't trigger that heuristic. (Note: Bitwarden on iOS may still create a duplicate rather than update; that's a known Bitwarden native-app limitation, out of our control.)
- **Client-Side Input Validation:** Centralized all form validation rules into `utils/validation.ts` (email regex, name/group-name lengths, expense title/amount limits, and two password tiers — lenient `validateLoginPassword` for existing passwords, strict `validateNewPassword` requiring 8+ chars with a letter and a number for new ones). Wired login, register, change-password, edit-profile, add/edit-expense, and create-group to the shared validators, adding max-amount/max-title parity to the edit-expense form and length validation to group creation. Added a reusable `PasswordStrengthMeter` (live 4-segment meter) shown on register and change-password.
- **Smart Invite Code Parsing:** The "Gruba Katıl" field now accepts the full pasted invite message or link (e.g. from WhatsApp) and auto-extracts the code via a new `parseInviteCode()` helper (`utils/invite.ts`) — matching `/invite/<code>`, then any URL's last path segment, then the last alphanumeric token, always normalized to upper-case. Parsing runs on paste (blobs with a link/whitespace) and again as a safety net on submit. The shared invite message was also updated to spell out the code for manual entry (superseded later in this sprint by the invite copy rewrite above).
- **Settlement & Greeting UX Tweaks:** Made the settlement action button perspective-aware — the debtor now sees **"Öde"** while the creditor still sees **"Ödendi"** (confirmation dialog unchanged; still a record-only action, no real transfer). Replaced the static "Merhaba, X" home header with a **time-of-day greeting** (Günaydın / İyi günler / İyi akşamlar / İyi geceler) derived from the device's local clock via a new `getGreeting()` helper.
- **Group Action Sheets Perf Fix:** Replaced the Tamagui `Sheet modal` used by the "Gruba Katıl" and "Yeni Grup" flows with the Reanimated-based custom `BottomSheet`, fixing the sluggish ~30fps open/close transitions on physical iOS devices. Purely a UI/animation swap — the props interface and all functionality (validation, submit, keyboard handling) are unchanged.
- **Alacak / Borç Breakdown Sheet:** The **Alacak** and **Borç** figures in the Genel Bakiye card are now tappable (with a chevron affordance). Tapping a non-zero figure filters the relevant groups by currency and either deep-links directly to settlement (single group) or opens the new `BalanceGroupsSheet` bottom sheet listing each contributing group with its per-group amount and a settlement deep-link. The sheet supports a `variant: 'debt' | 'credit'` prop so both sides share one component. The old `OwedGroupsSheet` was replaced by `BalanceGroupsSheet`, which the Ödenmemiş Borçların action card also uses.

Above the list (only when the user has at least one group) a summary panel renders, in order: an **Ödenmemiş Borçların** action card at the top (standalone red CTA; deep-links directly when there is only one owed group, otherwise opens a `BalanceGroupsSheet` bottom sheet listing each owed group with a settlement deep-link, shown only when debt exists); a combined overview card containing **Genel Bakiye** (per-currency credit/debt) and **Bu Ay** (the user's share of this month's expenses per currency) split by a hairline divider; and a **Son Hareketler** card with the 3 most recent expenses across all groups.
