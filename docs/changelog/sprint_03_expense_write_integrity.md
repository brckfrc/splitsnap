# Sprint #3: Expense Write Integrity (July 2026)

One migration (`20260727215500_expense_write_integrity.sql`) plus a client-side epsilon change. Everything below is about the same question: **can a client write numbers the server never agreed to?** Balances are derived entirely from `expense_shares` and `expense_payers`, so anything writable there is writable in the ledger.

- **Any Member Could Rewrite Who Paid (`expense_payers` RLS):** SEC-01 (`20260427000000`) hardened `expense_shares` so writes require being the expense creator or the group owner. When `expense_payers` arrived three months later in the multi-payer migration, the **pre-SEC-01** policy shape was copied and only `is_group_member()` was required. Any active member could `PATCH`/`DELETE`/`POST` payer rows on an expense someone else created and reassign who fronted the money, straight through PostgREST. The policies are now identical to the `expense_shares` ones. No client change.
- **The Expense RPCs Never Checked the Numbers:** `create_expense_with_shares` / `update_expense_with_shares` validated membership, title, `amount > 0` and split type, and then inserted whatever `p_shares` and `p_payers` JSON they were handed. Nothing required the shares to add up to the total, the payers to add up to the total, or the `user_id`s to belong to the group at all. An expense whose shares don't sum is the worst failure mode this app has: the group's balances never reach zero, the settlement screen shows a phantom debt forever, and there is no surface anywhere for the user to find or correct it.
  - A shared `validate_expense_allocations()` guard now runs over both arrays: valid payload shape, every amount `> 0`, no duplicate user, every `user_id` in the group, and the rounded total within one kuruş of `p_amount`. Also added: `p_shares` may not be empty, `p_paid_by` must be in the group, and `p_receipt_storage_path` must start with `<p_group_id>/` (Storage RLS derives the group from that first path segment, so a foreign path would attach an image nobody in the group can read).
  - **Membership deliberately ignores `left_at`.** An expense from before someone left still lists them and has to stay editable; the check exists to reject `user_id`s from outside the group, not to freeze history when a member leaves.
- **Any Group Owner Could Rewrite Any Expense in the Database:** not in the audit, found while writing the validation above. `update_expense_with_shares` looks up the expense to decide authorization, and the `and group_id = p_group_id` clause on that lookup, present since the Week 8 migration, was dropped when the RPC was rewritten for multi-payer (`20260726172500`). The function is `SECURITY DEFINER`, so RLS never re-checks it. That made this work: pass `p_group_id` = a group **you own** together with the id of an expense in **any other group**, and the `owner_id = auth.uid()` branch of the authorization check passes against your own group while the write lands on someone else's expense. Since every member can read the expense ids of their groups, any user who owns even one group could rewrite the title, amount, date, shares and payers of any expense they could see. The scoping clause is restored, and the pre-fix behaviour is pinned by a test.
- **One Money Epsilon (0.05 → 0.01):** the expense forms accepted a manual split that was off by up to 5 kuruş while the rest of the app treats 0.01 as equality. Now `MONEY_EPSILON` / `amountsMatch()` in `utils/validation.ts`, matching the server tolerance exactly. Keeping the client looser than the server would only turn a fixable form error into an opaque RPC rejection. Each member row already has a "fill the remaining amount" affordance, so hitting the total exactly is one tap. **Note for the 1.0.0 users still on the App Store:** their build keeps the old 5-kuruş tolerance, so a manual split with a 2–5 kuruş gap will now be refused by the server with a raw error code instead of silently saving a ledger that never balances. Rare, and the better of the two outcomes, but it is a live-user-visible change.
- **The Migrations Could Not Rebuild a Working Database:** running the full chain against a fresh Postgres produced a database where `authenticated` held **no DML grant on any `public` table** (only the inert `REFERENCES`/`TRIGGER`/`TRUNCATE` defaults) and could not execute `is_group_member` / `is_group_participant`, so every policy calling them raised `permission denied for function` instead of evaluating. Production works, which means those grants lived only on the hosted database and were never committed: a disaster-recovery restore, a second environment or any local test database was dead on arrival, and there was no reviewable record of who may touch what. The backlog entry suspected this about two functions; it was the entire schema.
  - `20260727223000_codify_role_grants.sql` writes the surface down, granting **exactly the operations that have a matching RLS policy** rather than a blanket `GRANT ALL`. So `expenses` gets no `DELETE` (removal is a soft delete), `group_members` gets no `INSERT` (joining goes through the RPC), `ai_usage` / `app_config` get nothing at all, and `anon` gets nothing anywhere.
  - **`activity_log` gets `SELECT` but deliberately not `INSERT`,** even though an insert policy exists from Week 3. The recorded design decision is that log rows come from database triggers so no missed call path or old build can leave gaps; withholding the grant keeps that enforceable, since it obliges the trigger functions to be `SECURITY DEFINER`. Whoever builds the activity feed should read that as a decision, not an oversight.
  - **Additive only** — it grants, never revokes, so it cannot change what the hosted database already allows. Verified by rebuilding from scratch: with the migration in place the write-integrity suite passes with no grants in its own fixture, which it previously needed to fake.
- **Verified against a real database, not just by reading:** `supabase/tests/expense_write_integrity_test.sql` sets up two groups, an owner, a plain member, an outsider and a departed member, then runs 19 checks as those users through `auth.uid()`. All 19 pass on the fixed schema. Re-run against the pre-fix definitions, 14 of them fail and the legitimate-behaviour checks still pass, which is what makes the three holes above confirmed rather than suspected. The file is standalone SQL (no test runner in this project yet) and rolls back at the end; see `supabase/README.md`.
- **Read-only production audit added:** `supabase/audit/expense_integrity_audit.sql` finds expenses whose shares or payers don't add up, per-group net balances that don't sum to zero, allocations belonging to non-members, and expenses with no payer row. The migration stops new bad rows but repairs nothing, so this is how you find out whether any group is already carrying a balance the app can never settle.
